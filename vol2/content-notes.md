# 第2回 勉強会の話す内容

このファイルを内容の正本とする。
`slides.md`は、ここにある主張を1枚1メッセージへ圧縮したもの。
聴衆はほぼ非エンジニアの学生。投影面では日常の言葉で言い、正式名は括弧で添える。

用語は正式名で呼び、説明のときだけ日常のたとえを添える（第1回の「エディタは、ファイルを読んで書く作業台」と同じ形）。

| 用語 | 投影で使うたとえ |
|---|---|
| コンテキスト | AIの作業机。一般知識は頭の中、今回の仕事の中身は机の上だけ |
| 圧縮（compaction） | 古い書類を1枚の要約に差し替える |
| CLAUDE.md | 新しく入った人に渡す申し送りメモ |
| rules | その棚を開けたときだけ目に入る注意書き |
| memory | AIが書き、人も直せる業務日誌 |
| skills | 棚にしまってある手順書。背表紙だけいつも見えている |
| hooks | 決まった場面で自動で動く装置。改札のゲートはPreToolUseの例 |
| settings.json | 運用設定をまとめた1枚。permissionsが入館証 |
| ハーネス | 馬具。同じ馬でも手綱と鞍の付け方で走り方が変わる |
| エージェントループ | 料理して、味見して、直す |
| 完了条件 | 「どうなったら終わりか」の取り決め |

たとえは理解の入口であって、定義ではない。質問が出たら正式な説明（下の各節）へ戻す。

## 0. この勉強会で持ち帰ってほしいこと

AIが「何を読んで」動いているかが分かり、同じ頼み方でも読んでいるものが違えば結果が変わると理解すること。
守らせたいことの置き場を、お願いする（メモ、日記）、条件つきで渡す（条件つきメモ、手順書）、機械で止める（見張り、許可リストの禁止）の3段で選べるようになること。

本編49分、実演6分、質疑5分。専門用語は検索用に一度だけ言い、以降は日常の言葉で話す。

## 導入（1〜5枚目）

同じ「ログインの不具合を直して」でも、環境Aは直して報告だけ、環境Bは動作チェックを走らせて通してから報告する。
違いは頼み方ではなく、AIが最初に読む申し送りメモ（「直したら動作チェックを通す」と書いてある）と、AIを縛る柵。
第1回の「処理の終了と作業の完了は別」を、今回は設定の側から解く。
5枚目で「今日のAI」を定義する。チャットのAI（1往復で終わり、手元のファイルは見えない）に対し、Claude CodeやCodexはパソコンの中でファイルを読み書きし、コマンドを実行し、結果を見て続ける。一般知識は頭の中にあり、今回の仕事に関する情報は机の上にあるものだけ。

## 1. AIの机の上（6〜13枚目）

### 机の上（コンテキスト）

AIは机の上に置いてある文章しか読めない。3種類に分けて説明する。

1. 取扱説明書。製品側が最初から置いている。私たちには見えない
2. 申し送りメモと日記。私たちが書いた指示、AIが自分で書いた学び、手順書の目次
3. 会話と作業の結果。頼んだこと、読んだファイル、実行した結果

机には広さの上限がある。量はトークン（文字数のような単位。日本語1〜2文字で1トークンほど）で数える。
AIは返事をするたびに、机の上を全部読み直している。

### 頼む前の中身（実演1）

8枚目は2026-09-21に私の環境で`/context`を実行した実画面。取扱説明書4.9k、道具の説明17.6k、メモと日記3.9k、手順書の目次6.2kなどで、合計約34kが頼む前から載っている。机の広さは約100万トークンなので、約3%。
9枚目の先頭の値はこの合計、以降の各行は公式ドキュメントの例。関係ない作業へ移るときは`/clear`で机を片づける。

### 片づけ（圧縮）

机がいっぱいになると、古い会話は要約に置き換わる。これを圧縮（compaction）と呼ぶ。自動でも走るし、`/compact`で自分でも起こせる。
メモと日記はファイルなので読み直される。会話で言っただけのことは要約に溶ける。読んだファイルは更新が新しい最大5件だけ読み直される。
結論は「残したい指示は、会話ではなくファイルへ」。

### 申し送りメモ（CLAUDE.md）

作業の最初にいちばん先に読まれる指示書。新しく入った人に渡す申し送りと同じ。
自分用は`~/.claude/CLAUDE.md`、プロジェクト用はそのフォルダの直下。作業を始めるとき（セッション開始時）に読まれ、片づけのあとも読み直される。
短く、具体的に。公式は200行以内を目安にしている。長い手順は手順書へ。`@path`で別ファイルを取り込める。AGENTS.mdは同じ役割の別名。

### 条件つきメモ（rules）

`.claude/rules/`に置く、1ファイル1話題のメモ。先頭に`paths`を書くと、当てはまるファイルを開いたときだけ机に載る。書かなければ申し送りメモと同じで常に載る。
効き方（AIが読んで従う）は申し送りメモと同じで、強制力が上がるわけではない。机を軽く保つための仕組み。

### 日記（memory）

AIが自分で書き、次の回に読み直すメモ。私が訂正したときなどに残す。
場所は`~/.claude/projects/<project>/memory/`。`MEMORY.md`が目次で、始めるときに読まれるのは目次の先頭200行か25KBの早い方まで。詳細は`user_*.md`、`feedback_*.md`、`project_*.md`、`reference_*.md`に分かれ、必要なときに開く。
`/memory`で中身を見て、人が書き換えてよい。私の環境には87件ある。

## 2. AIの動き方（14〜17枚目）

### 繰り返し（エージェントループ）

頼まれる、考える、道具を使う、結果を見る、を終わったと判断するまで繰り返す。
チャットは1往復で終わるが、AIは結果を見て自分で次を決める。1周ごとに結果が机に足される。
道具はファイルを読む・書く、コマンドを実行する、検索するなど。外部サービス（GitHubなど）につなぐ道具はMCPという仕組みで足せる。学生には名前だけでよい。

### 終わりの条件

「終わったかどうか」の決め方が、AIの止まる位置を決める。
「直して」だけなら修正して報告で止まる。申し送りメモに「直したら動作チェックを通す」とあれば、チェックを走らせ、失敗を読み、直し、通ってから止まる。
3枚目の環境AとBの差はここに落ちる。第1回の「指示の4項目」の完了条件も同じ役割。

### 回す仕組み（ループエンジニアリング）

人が毎回頼む代わりに、AIを回す仕組みそのものを設計する考え方。
Boris Cherny（Claude Code責任者）の「I don't prompt Claude anymore. I have loops running that prompt Claude and figuring out what to do.」という発言を、Addy Osmaniが記事にまとめた。2026年に広まった言い方。

設計するのは3つ。動き出すきっかけ（毎朝9時、変更が届いたとき、チェックが失敗したとき）、確かめる手段（動作チェック、書き方の自動点検、別のAIによる見直し）、記録と引き継ぎ。
15枚目の繰り返し（AIの中で回る）と、ここで言う回す仕組み（人が設計して外から回す）は別物で、口頭で一言切り替える。
どれも最終判断は人に残す。

## 3. ハーネス（18〜26枚目）

### ハーネス

AIの製品は「頭脳（モデル）」と「手綱・柵」でできている。頭脳以外の全部をハーネス（馬具の意味）と呼ぶ。Birgitta Böckeler（Thoughtworks、2026-04）の定義で、「Agent = Model + Harness」。
製品が最初から持つ手綱と柵（取扱説明書、標準の道具、机の片づけ、危ない操作の確認）と、私が足したものの2段で説明する。
手綱＝AIが読んで従うもの（申し送りメモ、条件つきメモ、日記、手順書）、柵＝機械で止めるもの（見張り、許可リストの禁じる）と定義し、以降この分け方で通す。
同じ頭脳でも、外側の作り方で結果が変わる。3枚目の差はここ。

### 事前と事後（ハーネスエンジニアリング）

手綱と柵には、動く前に効くもの（メモ、条件つきメモ、手順書、実行前の見張り、許可リストの禁じる）と、動いたあとに効くもの（実行後の見張り、動作チェック、書き方の自動点検、人の見直し）がある。
原文はguides（feedforward）とsensors（feedback）。人の確認をなくすのではなく、確認が要る場所へ人の目を集める。

### 手順書（skills）

必要なときだけ開く手順。`~/.claude/skills/<name>/SKILL.md`。
いつも机に載るのは1行の説明だけで、AIはそれで「今この手順書が要る」と判断する。本文は開いたときに読む。人が`/name`と打っても、AIが自分で選んでもよい。
いつも要る事実はメモ、長い手順は手順書、と分ける。例は議事録（会議メモから決定事項と担当・期限を抜き出す）。私の環境には20本（議事録、スライド作り、レビュー、税金の相談など）。

### 見張り（hooks）と実例（実演2）

決めた場面で、小さなプログラムを自動で走らせる仕組み。AIの判断とは関係なく動く。
場面の例は、頼んだ直後（UserPromptSubmit）、道具を使う直前（PreToolUse。止められる）、使った直後（PostToolUse）、返事の直前（Stop）。正式名は検索用に一度だけ言う。

23枚目は実例。24枚目でhookの中身（スクリプトと、settings.jsonへの登録）を見せ、「1つの条件から始めればよい」と伝える。実物は23枚目の画面を止めたblock-secret-bash-read.sh。ファイルを直接編集する経路は別のhook（block-env.sh）が見ている。「.env（パスワードなどが入るファイル）の中身を見せて」と頼むと、AIは中身を読むコマンドを組み立てたが、道具を使う直前の見張りが「ダメ」と返し、コマンドは走らなかった。AIは自分でも「値は読まない」と気をつけたが、見張りはAIの判断と関係なく止める。これが26枚目の「機械で止める」の証拠になる。

### 許可リスト（settings.json）

許す（allow）、禁じる（deny）、毎回聞く（ask）の3つの表と、見張りの登録、環境の設定値、使う頭脳の種類を書く。
自分用は`~/.claude/settings.json`で全プロジェクトに効く。プロジェクト用は`.claude/settings.json`でチームで共有する。
優先順位は組織、コマンド引数、プロジェクト（local、共有）、自分用の順だが、学生には「自分用とプロジェクト用がある」で十分。
禁じるに書いた操作はAIがやりたがっても実行されない。ただし書き方に穴があると抜けられる（4章の考え方1）。

### 強制力の段

確実に守らせたいものほど、下の段へ置く。

1. お願いする。メモ、日記。AIが読んで従う。忘れることもある
2. 条件つきで渡す。条件つきメモ、手順書。要るときだけ読ませる。効き方は1と同じ
3. 機械で止める。実行前の見張り、許可リストの禁じる。AIの判断と関係なく効く

公式ドキュメントも「メモと日記は文脈であって強制ではない。必ず止めたいならPreToolUse hookを」と書いている。

## 4. 私の環境（27〜33枚目）

### 全体像

投影では中身の例を見せ、数は注記に落とす。

- お願いする: 「日本語で要点から答える」「秘密は読まない」「保存の確定（commit）は頼まれたときだけ」。日記には訂正の記録
- 条件つきで渡す: 「ファイルの履歴（Git）を触るときだけ読むメモ」、手順書「スライド作り」「議事録」
- 機械で止める: 「パスワードのファイルを読むコマンドを止める」「終わる前に別のAIの検品を挟む」

実数（2026-09-21）: 申し送りメモ11行（共通原則49行を別ファイルで参照）、日記87件、条件つきメモ4本（実装、Git、秘密、道具の選び方）、手順書20本、見張り20本、許可リストの禁じる21件、毎回聞く19件、許す49件。

Claude（Anthropic）とCodex（OpenAI）の2製品で、同じメモと見張りを共有している。最初からこうだったわけではなく、困ったことが起きるたびに1つずつ足した。

### 考え方1: 3回言ったことは、お願いをやめて見張りにする

1回目は訂正し、AIが日記に残す。2回目も同じことが起きたら、日記は読まれても解釈が割れると分かる。3回目で見張りにし、機械で強制する。
実例は、本番（実際に人が使う側）の設定ファイル（render.yaml）、パスワードのファイル（.env）、作業用の一時フォルダの3つ。
今日の撮影中に、本番の設定ファイルの「禁じる」が別の道具（コマンド経由の書き換え）で抜けられる穴が見つかり、その日のうちに見張りを1本足した。お願いは忘れられる。実害が出たことは機械で止める側へ移す。

### 考え方2: 秘密は読ませない。3重にする

AIは悪気なく「確認のため」に秘密を読もうとする。机の上の文章はAI会社のサーバーへ送られ、会話の記録にも残る。だから読む前に止める。

1. 読む道具を禁じる。許可リストで、鍵やパスワードのフォルダを「読むの禁止」に
2. コマンド経由も止める。`cat .env`のように、コマンドで中身を出すのも見張りが止める
3. プログラム経由も止める。Pythonなどに読ませる抜け道も見張りが止める

実際に一度、道具のAPIキーが会話の記録へ流れたことがあり、2本目を足した。その後3本目の抜け道が見つかった。

### 考え方3: 「終わりました」の前に、見張りで確かめさせる

1. 見直しを挟む見張り。プログラムを変えたまま終わろうとしたら、別製品のAI（Codex）に検品させてから報告させる。今日のスライド作りでも5回発火し、そのたびに事実の誤りが見つかった
2. 別の案を探す見張り。新しいアイデアを共有したら、作り始める前に「もっと良い方法はないか」を1回調べさせる
3. 本当に終わったか確かめる見張り。保存や送信のあとに、実際の状態を別のコマンドで確認させる。以前「マージ完了」と報告されたのに完了していなかった事故から生まれた

### 考え方4: 毎回読ませる量は減らし、要るときだけ読ませる

最初は申し送りメモに全部書いていた。長くなり、関係ない作業でも毎回読み、守られる率も下がった。
今はメモ11行。手順は手順書へ、条件つきの話は条件つきメモへ。共通原則（49行）は別ファイルにして、ClaudeとCodexの両方から同じものを読ませ、2製品で方針が食い違わないようにしている。
頼む前の机は約34k。机が軽いほどAIは今の仕事に集中できる。学生には「まず10行から始めて、増やしすぎない」と伝える。

### 柵を作る順番

まず訂正する（AIが日記に残す。多くはこれで足りる）→ 繰り返すならメモに書く（申し送りメモ、条件つきメモ、手順書）→ 実害が出たら見張りにする（機械で止め、抜け道が見つかったら足す）。
最初から全部作らない。柵が多すぎると、AIも人も動きにくくなる。見張りは善意の事故を止める柵で、悪意のある回避を完全に防ぐものではない、と割り切っている。

## まとめ（34〜35枚目）

34枚目は言葉の一覧（今日の言い方と正式名の対応表）。配布用に残す。
35枚目は今日から試す3つ。Claude Codeを入れたパソコンが前提なので、入れ方は勉強会のあとに案内する。申し送りメモを10行書く、AIを1回訂正して日記に残ったか`/memory`で確かめる、`/context`を打って自分の机の上を見る。
